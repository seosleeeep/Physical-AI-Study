# ROS 2 Jazzy + Gazebo Harmonic 4륜 차량

Ubuntu 24.04에서 사용하는 ROS 2 기초 과제 소스. 2026-10-01에 실제 작업 공간의 4륜 버전을 복사한 스냅샷이다.

## 현재 구현 범위

- URDF: 차체, 운전석, 창문, 범퍼, 전후등, 타이어와 은색 휠 4개.
- 구동: Gazebo Harmonic의 DiffDrive 플러그인으로 네 바퀴 구동.
- 자동 실행: Gazebo 실행, 차량 생성, ROS–Gazebo bridge 실행을 하나의 launch로 수행.
- 토픽: `/cmd_vel`, `/odom`, `/clock`.
- RGB-D 카메라, RViz 설정, rosbag 기록/재생, CSV/TXT 저장 노드는 아직 구현하지 않았다.

## 1. 개념

### 파일 구조

```text
jazzy_four_wheel_car/
├── .gitignore
├── README.md
├── CODE_GUIDE.md
└── src/simple_car/
    ├── package.xml
    ├── CMakeLists.txt
```

| 파일 | 역할 |
|---|---|
| `package.xml` | 패키지 이름, 의존성, 빌드 방식 정의 |

| `launch/sim.launch.py` | Gazebo, 모델 생성, bridge 자동 실행 |

### 차량과 좌표계

X축은 앞쪽, Y축은 왼쪽, Z축은 위쪽이다. 길이는 m, 질량은 kg, 각도는 rad 단위다.

| 항목 | 값 |
|---|---|
| 차체 크기 | 0.60 × 0.30 × 0.10 m |
| 운전석 크기 | 0.28 × 0.25 × 0.13 m |
| 바퀴 반지름 / 폭 | 0.09 / 0.055 m |
| 앞뒤 바퀴 중심 X 위치 | +0.20 / -0.20 m |
| 좌우 바퀴 중심 Y 위치 | +0.19 / -0.19 m |
| 좌우 바퀴 간격 | 0.38 m |
| 앞뒤 바퀴 간격 | 0.40 m |
| 바퀴 중심 Z 위치 | 차체 기준 -0.045 m |

네 바퀴의 회전축은 Y축이다. 왼쪽 두 바퀴는 같은 명령을, 오른쪽 두 바퀴는 같은 명령을 받는다. 앞바퀴 조향 관절은 없으며 좌우 속도 차이와 접촉면의 미끄러짐으로 회전하는 스키드 스티어 방식이다.

이상적인 차동구동 계산은 다음과 같다.

```text
왼쪽 바퀴 각속도 = (v - ω × L / 2) / r
오른쪽 바퀴 각속도 = (v + ω × L / 2) / r
v: 전진 속도(m/s), ω: 회전 속도(rad/s)
L: 좌우 간격(0.38 m), r: 바퀴 반지름(0.09 m)
```

실제 시뮬레이션의 이동은 마찰과 미끄러짐의 영향을 받는다. `/odom`은 구동 플러그인의 주행 추정값이며 Gazebo 실제 위치를 직접 측정하는 센서는 아니다.

### 메시지 흐름

```text
ROS /cmd_vel → bridge → Gazebo DiffDrive → 네 바퀴 구동
ROS /odom    ← bridge ← DiffDrive의 위치·속도 추정
ROS /clock   ← bridge ← Gazebo 시뮬레이션 시간
```

## 2. 구현 과정 및 실행

### 기존 작업 공간에서 실행

이 스냅샷을 만든 실제 소스는 `~/jazzy_car_ws/src/simple_car`에 있다. 기존 실행 터미널에서 Ctrl+C로 Gazebo를 종료한 뒤 실행한다.

```bash
source /opt/ros/jazzy/setup.bash
cd ~/jazzy_car_ws
colcon build --packages-select simple_car
source install/setup.bash
ros2 launch simple_car sim.launch.py
```

`source`는 현재 터미널에 환경을 적용한다. `colcon build`는 파일을 설치하고, 설치 환경을 적용한 후 `ros2 launch`로 실행한다. URDF를 수정하면 다시 빌드하고 Gazebo를 재시작해야 새 모델이 생성된다.

### Git에서 내려받은 소스로 실행

이 저장소 루트는 ROS 2 작업 공간으로 사용할 수 있다. 저장소를 다운로드하거나 clone한 후 루트에서 실행한다.

```bash
source /opt/ros/jazzy/setup.bash
colcon build --packages-select simple_car
source install/setup.bash
ros2 launch simple_car sim.launch.py
```

필요한 환경이 설치되지 않은 PC에서는 먼저 Ubuntu 24.04용 ROS 2 Jazzy를 설치해야 한다. Jazzy가 설치된 상태에서 다음 도구를 설치할 수 있다.

```bash
sudo apt update
sudo apt install ros-jazzy-ros-gz python3-colcon-common-extensions
```

### 전진·회전·정지

두 번째 터미널에서 ROS 환경을 적용한 후 실행한다.

```bash
source /opt/ros/jazzy/setup.bash
# 초당 10번, 전진 속도 0.2 m/s 발행
ros2 topic pub --rate 10 /cmd_vel geometry_msgs/msg/Twist \
  "{linear: {x: 0.2}, angular: {z: 0.0}}"
```

Ctrl+C로 발행을 중단한 뒤 정지 명령을 보낸다. 발행 중단만으로 마지막 속도 명령이 해제되지 않을 수 있다.

```bash
ros2 topic pub --once /cmd_vel geometry_msgs/msg/Twist \
  "{linear: {x: 0.0}, angular: {z: 0.0}}"
```

회전 명령은 다음과 같다. 확인 후 Ctrl+C와 위 정지 명령을 사용한다.

```bash
ros2 topic pub --rate 10 /cmd_vel geometry_msgs/msg/Twist \
  "{linear: {x: 0.0}, angular: {z: 0.5}}"
```

### 토픽 확인

```bash
ros2 topic list
ros2 topic echo /odom --once
```

`pose.pose.position`은 추정 위치, `twist.twist.linear`는 선속도, `twist.twist.angular`는 각속도다.

### Git에 기록

이 폴더에 기존 `.git`이 없다면 저장소 루트에서 실행한다.


`git init`은 로컬 저장소 생성, `git add`는 기록할 파일 선택, `git commit`은 버전 저장이다. 원격 GitHub 등으로 보내려면 사용자가 지정한 저장소 주소를 연결한 후 push한다. 이 소스 묶음에는 원격 주소나 계정 정보가 들어 있지 않다.

# ROS 2 Jazzy + Gazebo Harmonic 4륜 차량

Ubuntu 24.04에서 URDF로 4륜 차량을 만들고, Gazebo의 `DiffDrive` 플러그인으로 주행하는 ROS 2 기초 과제이다.

## 1. 구현 범위

- 차체, 운전석, 창문, 범퍼, 전조등, 후미등

- `/cmd_vel`로 속도 명령 전달
- `/odom`으로 추정 위치·속도 확인

## 2. 기본 개념

### 차량 구동 방식

왼쪽 바퀴 두 개와 오른쪽 바퀴 두 개를 각각 같은 속도로 구동한다. 좌우 바퀴 속도 차이를 이용해 회전하는 **4륜 스키드 스티어 방식**이다.

앞바퀴 조향 관절은 없으며, 회전할 때 바퀴와 바닥 사이에서 미끄러짐이 발생한다.

```text
ROS 2 /cmd_vel → Bridge → Gazebo DiffDrive → 바퀴 4개 회전
ROS 2 /odom    ← Bridge ← Gazebo 주행 위치·속도 추정
ROS 2 /clock   ← Bridge ← Gazebo 시뮬레이션 시간
```

### URDF 주요 요소

| 요소 | 의미 |
|---|---|
| `link` | 차체나 바퀴 같은 부품 |
| `joint` | 부품 사이의 연결과 운동 방식 |
| `visual` | 화면에 보이는 형상 |
| `collision` | 충돌 계산에 사용하는 형상 |
| `inertial` | 질량과 회전 관성 |
| `origin` | 위치와 방향 |
| `axis` | 관절의 회전축 |
| `gazebo` | Gazebo 전용 설정과 플러그인 |

### 좌표와 단위

- X축: 차량 앞쪽
- Y축: 차량 왼쪽
- Z축: 위쪽
- 길이: m
- 질량: kg
- 각도: rad
- 선속도: m/s
- 각속도: rad/s

## 4. 전체 코드

### 4.1 `package.xml`

패키지 정보와 빌드·실행에 필요한 의존성을 정의한다.

```xml
<?xml version="1.0"?>
<package format="3">
  <name>simple_car</name>
  <version>0.0.1</version>

  <description>
    Beginner differential drive car for Gazebo Harmonic
  </description>

  <maintainer email="rrc@example.com">rrc</maintainer>
  <license>Apache-2.0</license>

  <buildtool_depend>ament_cmake</buildtool_depend>

  <exec_depend>ros_gz_sim</exec_depend>
  <exec_depend>ros_gz_bridge</exec_depend>
  <exec_depend>launch</exec_depend>
  <exec_depend>launch_ros</exec_depend>
  <exec_depend>ament_index_python</exec_depend>

  <export>
    <build_type>ament_cmake</build_type>
  </export>
</package>
```

| 항목 | 역할 |
|---|---|
| `ament_cmake` | 패키지 빌드 및 설치 |
| `ros_gz_sim` | Gazebo 실행과 모델 생성 |
| `ros_gz_bridge` | ROS 2와 Gazebo 사이의 메시지 변환 |
| `launch`, `launch_ros` | Launch 파일 실행 |
| `ament_index_python` | 설치된 패키지 경로 검색 |

`package.xml`에 의존성을 선언하는 것만으로 해당 프로그램이 자동 설치되지는 않는다.

### 4.2 `CMakeLists.txt`

URDF와 Launch 파일을 패키지 설치 경로로 복사하도록 설정한다.

```cmake
cmake_minimum_required(VERSION 3.8)

project(simple_car)

find_package(ament_cmake REQUIRED)

install(
  DIRECTORY urdf launch
  DESTINATION share/${PROJECT_NAME}
)

ament_package()
```

빌드 후 Launch 파일은 `src`의 원본이 아니라 **설치 경로에 복사된 URDF**를 사용한다. 따라서 모델을 수정한 뒤에는 다시 빌드해야 한다.

### 4.4 `launch/sim.launch.py`

Gazebo 실행, 차량 생성, ROS–Gazebo bridge 실행을 자동화한다.

```python
from pathlib import Path

from ament_index_python.packages import get_package_share_directory
from launch import LaunchDescription
from launch.actions import IncludeLaunchDescription
from launch.launch_description_sources import PythonLaunchDescriptionSource
from launch_ros.actions import Node


def generate_launch_description():
    # 설치된 패키지의 share 경로 검색
    car_share = Path(get_package_share_directory("simple_car"))
    gz_share = Path(get_package_share_directory("ros_gz_sim"))

    # 빈 Gazebo 월드를 실행
    # -r: 시뮬레이션을 즉시 시작
    gazebo = IncludeLaunchDescription(
        PythonLaunchDescriptionSource(
            str(gz_share / "launch" / "gz_sim.launch.py")
        ),
        launch_arguments={
            "gz_args": "-r empty.sdf"
        }.items(),
    )

    # URDF 파일을 사용해 차량 생성
    spawn = Node(
        package="ros_gz_sim",
        executable="create",
        arguments=[
            "-world", "empty",
            "-file", str(car_share / "urdf" / "car.urdf"),
            "-name", "simple_car",
            "-z", "0.2",
        ],
        output="screen",
    )

    # ROS 2와 Gazebo 사이의 메시지 변환
    bridge = Node(
        package="ros_gz_bridge",
        executable="parameter_bridge",
        arguments=[
            "/cmd_vel@geometry_msgs/msg/Twist]gz.msgs.Twist",
            "/odom@nav_msgs/msg/Odometry[gz.msgs.Odometry",
            "/clock@rosgraph_msgs/msg/Clock[gz.msgs.Clock",
        ],
        output="screen",
    )

    return LaunchDescription([
        gazebo,
        spawn,
        bridge,
    ])
```

#### Launch 해설

- `generate_launch_description()`은 ROS 2 Launch가 실행할 작업 목록을 반환한다.
- `IncludeLaunchDescription`은 다른 패키지의 Launch 파일을 포함한다.
- `Node`는 지정된 ROS 실행 파일을 실행한다.
- `create`는 Gazebo 생성 서비스를 기다린 뒤 URDF 모델을 추가한다.
- `-z 0.2`는 차량 기준점을 높이 0.2m에서 생성한다.
- `output="screen"`은 실행 로그를 터미널에 표시한다.

#### Bridge 해설

| 토픽 | ROS 메시지 | 방향 |
|---|---|---|
| `/cmd_vel` | `geometry_msgs/msg/Twist` | ROS → Gazebo |
| `/odom` | `nav_msgs/msg/Odometry` | Gazebo → ROS |
| `/clock` | `rosgraph_msgs/msg/Clock` | Gazebo → ROS |

Bridge 인수에서 `]`는 ROS→Gazebo, `[`는 Gazebo→ROS 전달을 의미한다.

## 6. 주행 명령

별도 터미널에서 ROS 2 환경을 적용한다.

```bash
source /opt/ros/jazzy/setup.bash
```

### 전진

초당 10번, 전진 속도 0.2m/s를 발행한다.

```bash
ros2 topic pub --rate 10 /cmd_vel geometry_msgs/msg/Twist \
  "{linear: {x: 0.2}, angular: {z: 0.0}}"
```

### 회전

전진 속도 0m/s, 회전 속도 0.5rad/s를 발행한다.

```bash
ros2 topic pub --rate 10 /cmd_vel geometry_msgs/msg/Twist \
  "{linear: {x: 0.0}, angular: {z: 0.5}}"
```

### 정지

주행 명령을 발행하던 터미널에서 `Ctrl+C`를 누른 뒤 아래 명령을 보낸다. 발행 중단만으로 마지막 속도 명령이 해제되지 않을 수 있다.

```bash
ros2 topic pub --once /cmd_vel geometry_msgs/msg/Twist \
  "{linear: {x: 0.0}, angular: {z: 0.0}}"
```

### 위치·속도 확인

```bash
ros2 topic echo /odom --once
```

| 출력 항목 | 의미 |
|---|---|
| `pose.pose.position` | 추정 위치 |
| `pose.pose.orientation` | 추정 방향을 나타내는 Quaternion |
| `twist.twist.linear` | 선속도 |
| `twist.twist.angular` | 각속도 |

`/odom`은 구동 플러그인의 주행 추정값이다. Gazebo의 실제 위치와 항상 일치하는 정답값은 아니다.

## 11. ROS 2 컨트롤러를 이용한 차량 주행

### 11.1 개념 — 컨트롤러와 플러그인의 차이

플러그인은 Gazebo에 기능을 추가하는 모듈이고, 컨트롤러는 목표 명령을 받아 관절을 제어하는 구성 요소이다. **플러그인이 제어 기능을 직접 수행할 수도 있으므로 두 용어는 완전히 대립하는 개념이 아니다.**

이번 과제에서 사용한 두 방식은 다음과 같다.

| 구분 | 이전 방식 | 현재 방식 |
|---|---|---|
| 구동 담당 | Gazebo `DiffDrive` 플러그인 | ROS 2 `diff_drive_controller` |
| Gazebo 연결 | 플러그인이 직접 바퀴 구동 | `gz_ros2_control` 플러그인이 연결 |
| 컨트롤러 관리 | 별도 ROS 컨트롤러 관리 없음 | `controller_manager`가 로드·활성화 |
| 입력 토픽 | `/cmd_vel` | `/diff_drive_controller/cmd_vel` |
| 메시지 | `Twist` | `TwistStamped` |

현재 구성에서도 Gazebo 연결에는 플러그인을 사용하지만, **바퀴 구동 명령을 계산하는 역할은 ROS 2 컨트롤러가 담당한다.**

```text
목표 속도 입력
    ↓
diff_drive_controller
    ↓
ros2_control 관절 제어 인터페이스
    ↓
gz_ros2_control 플러그인
    ↓
Gazebo 바퀴 구동
```

### 11.2 구현 과정 — 컨트롤러 활성화 확인

차량이 Gazebo에 생성된 상태에서 새 터미널을 열고 실행하였다.

```bash
source /opt/ros/jazzy/setup.bash
ros2 control list_controllers
```

다음 두 항목이 `active`인지 확인한다.

```text
joint_state_broadcaster  ...  active
diff_drive_controller   ...  active
```

- `joint_state_broadcaster`: 바퀴 관절의 위치와 속도를 발행한다.
- `diff_drive_controller`: 차량의 목표 속도를 좌우 바퀴 회전 속도로 변환한다.
- `active`: 해당 컨트롤러가 활성화된 상태이다.

### 11.3 구현 과정 — 전진

전진 속도 **0.2m/s**, 회전 속도 **0rad/s**를 전달하였다.

```bash
ros2 topic pub --rate 10 --use-sim-time \
  /diff_drive_controller/cmd_vel geometry_msgs/msg/TwistStamped \
  "{header: auto, twist: {linear: {x: 0.2}, angular: {z: 0.0}}}"
```

| 항목 | 의미 |
|---|---|
| `--rate 10` | 초당 10번 명령 발행 |
| `--use-sim-time` | Gazebo 시뮬레이션 시간 사용 |
| `TwistStamped` | 시간 정보가 포함된 속도 메시지 |
| `header: auto` | 메시지에 현재 시간 자동 입력 |
| `linear.x` | 전진 속도, 단위 m/s |
| `angular.z` | 회전 각속도, 단위 rad/s |

### 11.4 구현 과정 — 곡선 주행

전진 명령을 `Ctrl+C`로 종료한 뒤, 전진하면서 좌회전하는 명령을 전달하였다.

```bash
ros2 topic pub --rate 10 --use-sim-time \
  /diff_drive_controller/cmd_vel geometry_msgs/msg/TwistStamped \
  "{header: auto, twist: {linear: {x: 0.2}, angular: {z: 0.3}}}"
```

컨트롤러가 오른쪽 바퀴를 왼쪽보다 빠르게 회전시켜 차량이 왼쪽으로 휘어 이동한다. 현재 모델은 앞바퀴 조향 없이 좌우 바퀴 속도 차이로 회전하는 **4륜 스키드 스티어 방식**이다.

회전이 가능하도록 바퀴의 횡방향 마찰을 낮추었다. 이 방식은 회전 중 접촉면의 미끄러짐이 발생한다.

### 11.5 구현 과정 — 정지

주행 명령을 `Ctrl+C`로 종료한 뒤, 선속도와 각속도를 모두 0으로 전달하였다.

```bash
ros2 topic pub --once --use-sim-time \
  /diff_drive_controller/cmd_vel geometry_msgs/msg/TwistStamped \
  "{header: auto, twist: {linear: {x: 0.0}, angular: {z: 0.0}}}"
```

`--once`는 명령을 한 번 발행한다. 또한 현재 컨트롤러에는 새 명령이 없으면 **시뮬레이션 시간 0.5초 후 정지**하도록 시간 제한을 설정하였다.

## 12. 주행 결과 검증

### 12.1 확인 방법

컨트롤러의 추정 속도와 바퀴 관절 상태는 다음 명령으로 확인할 수 있다.

```bash
# 추정 선속도·각속도 확인
ros2 topic echo /diff_drive_controller/odom --field twist.twist
```

조회 종료 후 다음 명령을 실행한다.

```bash
# 네 바퀴의 관절 상태 확인
ros2 topic echo /joint_states --once
```

Odometry는 바퀴 회전으로 계산한 추정값이다. 실제 이동 검증에는 Gazebo 모델 위치와 방향의 변화도 사용하였다.

```bash
gz topic -e -t /world/empty/dynamic_pose/info
```

출력에서 `name: "simple_car"`인 모델의 위치·방향과 시뮬레이션 시간을 비교한다.

### 12.2 검증 결과

별도 Gazebo 테스트 환경에서 측정한 결과이며, 이후 사용자 화면에서도 정상 동작을 확인하였다.

| 동작 | 명령 | Gazebo 실제 측정 |
|---|---|---|
| 직진 | 0.2m/s | 약 0.2000m/s |
| 곡선 주행 | 0.2m/s, 0.3rad/s | 약 0.2062m/s, 0.2621rad/s |
| 정지 | 0m/s, 0rad/s | 측정 구간에서 이동·회전 없음 |

곡선 주행의 선속도는 구간 양 끝점의 변위를 시간으로 나눈 평균값이다. 회전 중에는 바퀴 미끄러짐과 접촉 동역학의 영향으로 명령값과 실제 이동값에 차이가 발생하였다.

> ROS 2의 `diff_drive_controller`를 활성화하고 `TwistStamped` 메시지로 목표 속도를 전달하였다. 4륜 차량의 직진, 곡선 주행, 정지 동작을 확인하였으며, 직진 구간의 실제 평균 속도가 명령 속도 0.2m/s와 일치함을 확인하였다.

# RGB-D 카메라 부착, RViz 센서 확인 및 방향키 주행

## 1. 개념

RGB-D 카메라는 컬러 영상(RGB)과 픽셀별 깊이(Depth)를 제공한다. 깊이와 카메라 내부 파라미터를 이용하면 물체 표면을 3차원 점군(PointCloud)으로 표현할 수 있다.

이번 실습에서는 Gazebo의 가상 카메라 데이터를 `ros_gz_bridge`로 ROS 2에 전달하고, RViz에서 영상과 점군을 확인했다.

| 토픽 | 메시지 형식 | 내용 |
|---|---|---|
| `/camera/image` | `sensor_msgs/msg/Image` | RGB 컬러 영상 |
| `/camera/depth_image` | `sensor_msgs/msg/Image` | 픽셀별 깊이, m 단위 |
| `/camera/camera_info` | `sensor_msgs/msg/CameraInfo` | 해상도 및 카메라 내부 파라미터 |
| `/camera/points` | `sensor_msgs/msg/PointCloud2` | XYZ 좌표와 색상을 가진 점군 |

깊이는 광축 방향의 거리다. 측정 범위 밖에는 `inf` 같은 비유효 값이 포함될 수 있다.

## 2. 구현 과정

### 2.1 카메라 부착 및 센서 설정

기존 차량에 `camera_link`와 고정 관절을 추가했다. 카메라는 `base_link` 기준 `(0.34, 0, 0.10)m`에 부착하고 차량 전방을 바라보도록 설정했다.

`car_rgbd.urdf`의 핵심 센서 설정은 다음과 같다. 아래 코드는 기존 파일의 일부이며, 전체 URDF를 대체하는 코드는 아니다.

```xml
<gazebo reference="camera_link">
  <sensor name="rgbd_camera" type="rgbd_camera">
    <always_on>true</always_on>
    <update_rate>10</update_rate>
    <topic>/camera</topic>
    <gz_frame_id>camera_link</gz_frame_id>
    <camera>
      <horizontal_fov>1.0471975512</horizontal_fov>
      <optical_frame_id>camera_link</optical_frame_id>
      <image>
        <width>320</width>
        <height>240</height>
        <format>R8G8B8</format>
      </image>
      <clip>
        <near>0.1</near>
        <far>8</far>
      </clip>
    </camera>
  </sensor>
</gazebo>
```

- `update_rate`: 센서 갱신 주기를 10Hz로 설정한다. 실제 수신 주기는 실행 성능에 따라 달라질 수 있다.
- `horizontal_fov`: 수평 시야각으로, 약 60도에 해당한다.
- `image`: 320×240 컬러 영상으로 설정한다.
- `clip`: 근거리·원거리 범위를 0.1~8m로 설정한다.

월드에는 카메라 렌더링을 위한 Sensors 시스템과 확인용 빨강·파랑·초록 블록을 추가했다.

```xml
<plugin filename="gz-sim-sensors-system"
        name="gz::sim::systems::Sensors">
  <render_engine>ogre2</render_engine>
</plugin>
```

### 2.2 ROS 2 연결 및 RViz 설정

`rgbd.launch.py`에서 센서 토픽의 Gazebo → ROS 2 bridge를 실행한다. 다음은 RGB 영상 bridge 인자 예시다.

```python
"/camera/image@sensor_msgs/msg/Image[gz.msgs.Image"
```

`[`는 Gazebo에서 ROS 2로 전달하는 방향을 뜻한다. Depth, CameraInfo, PointCloud2도 각각 연결했다.

영상과 CameraInfo는 ROS 카메라 좌표계인 `camera_optical_frame`을 사용한다. Gazebo 점군은 X축 전방 좌표로 생성되므로 `camera_link`를 사용하고, 두 좌표계 사이의 회전은 URDF의 고정 관절로 정의했다. bridge의 프레임 이름 변경만으로 XYZ 좌표가 회전되는 것은 아니다.

| RViz 항목 | 설정 |
|---|---|
| Fixed Frame | `base_link` |
| RGB Image | `/camera/image` |
| Depth Image | `/camera/depth_image` |
| PointCloud2 | `/camera/points`, XYZ / RGB8 |
| 센서 토픽 Reliability | Best Effort |

Depth Image는 자동 정규화를 끄고 표시 범위를 0~4m로 설정했다. 유효한 값은 가까울수록 어둡고 멀수록 밝게 표시된다. 비유효 픽셀의 검은색을 거리 0m로 해석하면 안 된다. 표시 범위는 센서의 측정 범위와 별개다.

### 2.3 실행 명령

기존 시뮬레이션 launch를 종료한 뒤 다음을 실행한다.

```bash
source /opt/ros/jazzy/setup.bash
source ~/jazzy_car_ws/install/setup.bash
ros2 launch simple_car rgbd.launch.py
```

두 `source` 명령은 ROS 2와 실습 패키지의 실행 환경을 불러온다. launch는 Gazebo, 차량, 컨트롤러, 센서 bridge 및 RViz를 함께 실행한다.

센서 토픽과 메시지 형식은 별도 터미널에서 확인한다.

```bash
source /opt/ros/jazzy/setup.bash
ros2 topic list | rg '^/camera/'
ros2 topic echo /camera/depth_image --once --field encoding
ros2 topic echo /camera/camera_info --once
```

`--once`는 메시지 하나만 출력하고 종료한다. `--field encoding`은 영상 형식만 출력하며, 깊이 영상의 결과는 `32FC1`이다. 이는 픽셀당 32비트 실수 하나로 깊이를 저장한다는 뜻이다.

### 2.4 방향키 조종

Gazebo와 RViz를 켜둔 상태에서 새 터미널로 조종창을 실행한다. 기존 `ros2 topic pub`가 실행 중이면 먼저 Ctrl+C로 종료한다.

```bash
source /opt/ros/jazzy/setup.bash
source ~/jazzy_car_ws/install/setup.bash
ros2 run simple_car keyboard_drive.py
```

조종창을 클릭한 상태에서 방향키를 누른다.

| 입력 | 동작 | 명령값 |
|---|---|---|
| ↑ / ↓ | 전진 / 후진 | `linear.x = ±0.15 m/s` |
| ← / → | 좌회전 / 우회전 | `angular.z = ±0.4 rad/s` |
| ↑ + ← 또는 → | 전진하며 회전 | 선속도와 각속도를 함께 입력 |
| 방향키 모두 놓기 | 정지 | 두 명령값 0 |
| Space | 정지 유지 | 방향키를 모두 놓으면 해제 |
| 다른 창 클릭 | 정지 | 포커스 상실 시 0 발행 |
| Esc 또는 창 닫기 | 정지 후 종료 | 0 발행 후 종료 |

`keyboard_drive.py`는 Tkinter의 키 입력을 읽어 `TwistStamped`를 약 10Hz로 `/diff_drive_controller/cmd_vel`에 발행한다. 시간은 Gazebo의 시뮬레이션 시간을 사용한다.

핵심 코드는 다음과 같다. 전체 코드에는 창 구성, 키 해제 및 정지 처리가 추가되어 있다.

```python
def command_for_keys(keys, linear_speed=0.15, angular_speed=0.4):
    v = linear_speed * (int('Up' in keys) - int('Down' in keys))
    w = angular_speed * (int('Left' in keys) - int('Right' in keys))
    return v, w

def publish(self, v, w):
    msg = TwistStamped()
    msg.header.stamp = self.node.get_clock().now().to_msg()
    msg.twist.linear.x = v
    msg.twist.angular.z = w
    self.publisher.publish(msg)
```

서로 반대인 키를 동시에 누르면 해당 축의 명령이 상쇄된다. 컨트롤러는 선속도·각속도를 좌우 바퀴 속도로 변환하고, `gz_ros2_control` 플러그인은 바퀴 명령과 상태를 Gazebo에 연결한다.

## 3. 검증 결과

### 3.1 센서 및 표시 확인

- RGB, Depth, CameraInfo, PointCloud2 메시지 수신을 확인했다.
- RGB는 320×240의 `rgb8`, Depth는 320×240의 `32FC1`이었다.
- RViz에서 차량 모델, 컬러 영상, 깊이 영상 및 색상 점군이 표시되었고 `Global Status: Ok`를 확인했다.
- 사용자의 Gazebo·RViz 화면에서도 차량 앞의 세 블록과 센서 표시를 확인했다.
- 별도 검증 시뮬레이션에서 초기 정면 깊이는 약 1.4600002m였다. 빨간 블록 앞면 X=1.8m에서 카메라 X=0.34m를 뺀 기대값 1.46m와 일치했다. 중앙 점군의 X좌표도 약 1.46m였다.

### 3.2 주행 중 확인할 값

방향키 조종으로 실제 차량 이동을 확인했다. 센서 검증에서는 다음 변화를 관찰한다.

| 확인 대상 | 전진 또는 회전할 때 관찰할 내용 |
|---|---|
| RGB Image | 접근 시 물체가 커지고, 회전 시 물체의 영상 위치가 바뀜 |
| Depth Image | 접근 시 해당 물체의 깊이값이 감소함 |
| PointCloud2 | 차량 기준 물체의 상대 위치가 달라짐 |
| Odometry | 선속도·각속도가 주행 입력에 따라 변함 |

속도는 별도 터미널에서 확인한다.

```bash
source /opt/ros/jazzy/setup.bash
ros2 topic echo /diff_drive_controller/odom --field twist.twist
```

로그를 실행한 뒤 조종창을 다시 클릭한다. ↑는 `linear.x` 약 +0.15, ↓는 약 −0.15, ←는 `angular.z` 약 +0.4, →는 약 −0.4를 기대하며, 정지하면 두 값이 0에 가까워지는지 확인한다.

이 값은 바퀴 상태로 추정한 속도다. 미끄러짐이 있을 수 있으므로 Gazebo에서의 실제 이동 속도와 완전히 같다고 단정하지 않는다. 이번 조종 확인은 차량 이동을 확인한 것이며, 방향키 주행 중의 수치 오차 측정은 별도 검증이 필요하다.
